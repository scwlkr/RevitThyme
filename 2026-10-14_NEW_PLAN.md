# RevitThyme — defining the product

I think we're arriving at a much clearer vision. But there are a few things I'd change about your proposal, including one architectural assumption that could cause major problems.

The most important distinction I'd make is this:

RevitThyme should be a native Revit toolkit that happens to be exceptionally good at working with AI—not an AI application that happens to control Revit.

That gives us a product worth using even when somebody doesn't have Codex.

I see three fundamental pieces:

1. RevitThyme Core: The native C# toolkit, including utilities like View Range.
2. RevitThyme MCP: A first-class interface allowing AI agents to inspect and manipulate Revit.
3. RevitThyme Agent: An optional interface where users can interact with Codex directly inside RevitThyme.

All three belong in the same open-source repository, and I would distribute them together.

## First, three decisions I'd challenge

### 1. The copy → edit → merge idea has a serious problem

I agree with your two-way-door philosophy. I disagree with using a separate Revit file as the default implementation.

Revit doesn't have Git-style branch merging.

Autodesk explicitly notes that local copies of cloud-workshared models cannot easily be merged back into the original.

[image](https://www.google.com/s2/favicons?domain=https://www.autodesk.com\&sz=32)

Autodesk



Revit worksharing does support local editing and synchronization with a central model, but that is different from taking arbitrary changes in a detached project copy and selectively merging them back.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://help.autodesk.com\&sz=32)

Autodesk Help



I'd preserve the goal—easy experimentation and recovery—but design a better mechanism specifically for Revit.

### 2. A built-in Codex experience is worth pursuing

This part of your idea is stronger than I initially expected.

OpenAI has an official Codex App Server for building custom client applications. It supports authentication, conversations, approvals, and streamed agent events. Codex also supports signing in with ChatGPT for subscription-based access.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developers.openai.com\&sz=32)

OpenAI Developers

+1



This means we have a credible way to build a RevitThyme AI interface without creating our own agent framework or requiring every user to purchase API credits separately.

I'd use Codex's existing runtime rather than recreate it.

### 3. The visual planning idea is worth testing—but not as a required step

The concept is useful: before constructing complicated Revit geometry, have the AI define the intended shape, reference planes, dimensions, and parameters.

However, opening tldraw for every operation could make the product noticeably slower and more cumbersome.

There's also a licensing concern: the tldraw SDK is source-available, not permissively open source, and production use requires an appropriate license. That's a meaningful constraint for a freely distributed open-source product.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://tldraw.dev\&sz=32)

tldraw Docs



I'd retain the visual foresight concept while avoiding a hard dependency on tldraw.

## 1. The experience I'd want users to have

1. Install RevitThyme

   Download one Windows installer from GitHub Releases, or use a one-line PowerShell bootstrapper.

   The installer detects supported Revit versions, registers the add-in, and installs the CLI and MCP components.
2. Open Revit

   A new RevitThyme tab appears with its built-in tools. Everything works without AI.
3. Connect Codex

   Select "Connect Codex," sign in through the supported ChatGPT authentication flow, and verify the connection.

   No manual JSON configuration should be required for the built-in interface.
4. Start working

   The user can click View Range, ask Codex to change the active view, or automate repetitive tasks with reusable skills.
5. Review changes

   See what changed, inspect the result in Revit, and keep or reverse the operation.

I'd aim for this entire experience to take one installer and one sign-in.

### Packaging

One repository, one installer, one product. Not necessarily one executable.

Under the hood, the installer can include multiple components and different builds of the Revit add-in for supported Revit releases. Starting with Revit 2025+ avoids the older .NET Framework 4.8 integration requirements, although individual Revit releases still need compatibility testing.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://blog.autodesk.io\&sz=32)

Autodesk Developer Blog



For Windows, I favor a downloadable `.exe` installer first, with a PowerShell bootstrapper that downloads and verifies the GitHub Release artifact. A `winget` package can come later.

Don't build our own package manager or updater at this stage.

## 2. The architecture I'd settle on

RevitThyme — Native Application

WPF Tools

View Range, native panels, utility buttons

Agent Panel

Codex chat, skills, tasks, review

CLI

Scripting, diagnostics, automation

MCP Server

External AI compatibility

RevitThyme Operation Layer — C#

Typed operations, element inspection, geometry, execution, results

In-Revit Execution Host — C#

ExternalEvent, Revit transactions, document context

Autodesk Revit API

The operation layer is the key. Every interface should use the same implementations rather than duplicate them.

For instance, View Range should have one core implementation accessible from the WPF interface, CLI, and MCP.

For MCP, we'd use the official C# MCP SDK. Start with local stdio transport for Codex and a local communication bridge to the Revit add-in. HTTP can be considered later for additional integrations.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



### Why a CLI is still valuable

I'd definitely retain a CLI, but I wouldn't force AI to interact with Revit through it. MCP gives AI typed tool schemas; CLI gives humans and scripts predictable commands. Both call the same operation layer.

An illustrative future command could be:

```
revitthyme view-range get --active --json
```

This also gives contributors a convenient way to reproduce failures and test Revit operations without repeatedly navigating through UI menus.

## 3. What the Codex harness actually looks like

I'd call this feature RevitThyme Agent, rather than calling the entire application a harness.

The user sees a dockable panel, but behind it we run OpenAI's Codex App Server locally.

RevitThyme Agent — WPF

Conversation, skill selection, previews

App Server protocol

Codex App Server

AI runtime, threads, tool calling, authentication

MCP tool calls

RevitThyme MCP

Native Revit capabilities

This doesn't require us to write the agent runtime in TypeScript or Python. The C# application can communicate with the Codex App Server over its documented protocol.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developers.openai.com\&sz=32)

OpenAI Developers



There's also a relevant newer option: OpenAI documents Sign in with ChatGPT plan usage for open-source, locally hosted applications. This is a promising fit for RevitThyme, although we should verify its eligibility, limitations, and end-to-end Windows behavior before making it an installation requirement.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://developers.openai.com\&sz=32)

OpenAI Developers



I'd keep external Codex support available, too. Someone who already prefers the Codex CLI or ChatGPT desktop app should be able to connect to the same RevitThyme MCP server without using our built-in chat panel.

### Skills without creating another giant system

The built-in Agent should discover ordinary skill files, not invent a new skill format.

For example, a `create-revit-family` skill could describe how to select a family template, establish reference planes, create parameters, generate geometry, and verify the result.

Skills should be version-controlled and shareable. Personal or company-specific skills can live in a separate user folder.

This gives us repeatability without having to develop our own memory system, agent planner, or sophisticated orchestration framework.

## 4. How I'd implement your two-way-door idea

I'd use three different levels of reversibility.

| Situation                                  | Recommended approach                                         |
| ------------------------------------------ | ------------------------------------------------------------ |
| Small edits (parameters, dimensions, tags) | Revit transactions and a single undo operation               |
| Larger model changes                       | Capture the affected elements and show a before/after review |
| Experimental AI-generated code             | Execute against a disposable project copy first              |

Revit's `TransactionGroup` supports rolling back grouped changes or combining them into a single undo operation. Its temporary graphics API can also help display visual indicators without leaving permanent model elements.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://help.autodesk.com\&sz=32)

Autodesk Help

+1



A separate file remains useful, especially for experimenting with untrusted or untested geometry-generation code.

But when the user likes the result, we need a precise promotion mechanism. For some operations, we could rerun the same verified operation against the original model after checking that the relevant elements haven't changed. For other operations, copying elements across documents is possible but has significant limitations.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://help.autodesk.com\&sz=32)

Autodesk Help



The principle I'd adopt:

> Make experimentation inexpensive to reverse, but never pretend that Revit models support Git-style merging.

I also wouldn't spend the early development phase building an elaborate safety engine. A solid transaction wrapper, disposable test projects, automatic backups for high-risk operations, and clear execution results are sufficient foundations.

Arbitrary C# would remain a trusted feature because it can perform actions outside Revit's undo system.

## 5. The planning canvas — what I would actually build

This is the part I'd most like to experiment with.

Your underlying intuition makes sense: AI can benefit from decomposing complicated spatial work before manipulating the real model.

But there's a distinction between making the AI draw something and making the AI understand the constraints of something.

A sketch can help communicate intent. It doesn't necessarily improve geometric correctness.

### Your receptacle example

I'd have RevitThyme generate a compact specification first:

Receptacle family concept

Illustrative preview

Diagrammatic front view

Family constraints

Category: Electrical Fixture

Hosting: Wall-based

Width: Parameter

Height: Parameter

Reference planes: Center, edges

Geometry: Parametric

This concept describes appearance and design intent, not a fully defined Revit family or electrical connector configuration.

Here's the workflow I would experiment with:

User Request

"Create a parametric receptacle family"

Quick Planning

Define geometry, parameters, reference planes, constraints

Optional Visual Sketch

Simple WPF vector diagram when spatial planning helps

Generate Revit Family

Create native geometry and parametric relationships

Validate

Change parameters, inspect the geometry, check constraints

The key is that the planning representation would record real intended constraints, not just decorative sketches.

For a family, successful parametric behavior matters far more than whether the initial canvas looked convincing.

### Should we use tldraw?

Not initially.

I'd first prototype simple WPF geometry and a short planning record. We already need WPF graphics for View Range.

If we later discover that editing complex spatial diagrams really improves results, we can evaluate a richer canvas system, including tldraw.

I'd make this behavior opt-in or automatically selected only for genuinely complex work.

The AI should never need to draw a diagram before renaming twelve doors.

## 6. What should our second native tool be?

I looked through Revit community discussions for practical missing functionality.

One request particularly caught my attention: automatically placing useful room width and depth dimensions while leaving space for the room tag. It's a good, narrowly scoped architectural tool.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.reddit.com\&sz=32)

Reddit

Room Dimensions

A one-click tool that detects room boundaries and places clear dimensions showing the room's width and depth.

Start with rectangular rooms, then expand to more complex shapes.

It would also be a useful MCP test because the AI would need to inspect room geometry, identify dimension references, create Revit elements, and verify the results.

Existing commercial and community tools already address parts of automated dimensioning, so I wouldn't market it as something nobody has done before. The opportunity is an excellent open-source implementation with both button and AI access.

Our initial native tools would therefore be View Range and Room Dimensions.

## 7. One thing I definitely want to preserve: the Cabin Eval

From our other evaluation discussion, we already have a useful benchmark concept.

I think it should become an important part of the RevitThyme repository, not just a one-time experiment.

The Cabin Eval gives Codex an assignment to construct a 14′ × 16′ cabin with 9′ walls, a gable roof, floor, door, two window types, electrical devices, appliances, dimensions, and parametric relationships.

Then an independent C# evaluator examines the actual Revit model—not the AI's description of what it thinks it created.

Cabin Eval scoring

Proposed 100-point rubric

# 100

Geometry

25 pts

BIM Accuracy

25 pts

Parametric Behavior

35 pts

Model Integrity

15 pts

The evaluator also changes the cabin length from 14′ to 18′ in a temporary test model and checks whether its parametric relationships behave correctly.

Execution time, tool calls, and errors are recorded separately.

This is valuable for two reasons.

First: It creates an objective benchmark for whether MCP changes actually improve real model creation, rather than merely exposing more tools.

Second: The evaluator could eventually evolve into a standalone Revit model quality-checking utility.

I would add a much smaller smoke-test suite first, then bring in the full Cabin Eval once dynamic C# execution is functioning.

## 8. Open-source repository and development order

I'd organize the repository approximately like this:

```
RevitThyme/
├── src/
│   ├── RevitThyme.Addin/       # Revit integration, ribbon
│   ├── RevitThyme.Core/        # Shared operations
│   ├── RevitThyme.UI/          # WPF tools and Agent panel
│   ├── RevitThyme.Cli/         # CLI
│   ├── RevitThyme.Mcp/         # MCP server
│   └── RevitThyme.Codex/       # Codex app-server client
├── skills/                     # Bundled agent skills
├── tests/
│   ├── Unit/
│   ├── RevitIntegration/
│   └── CabinEval/
├── installer/
├── docs/
├── .github/
├── README.md
├── CONTRIBUTING.md
└── LICENSE
```

A contributor should be able to understand the architecture, compile the project, and add a Revit tool without having to understand the Codex runtime.

The README should include screenshots or a demo GIF, installation instructions, supported Revit versions, an architecture diagram, and a clear contribution invitation. GitHub issue templates, a small set of labels such as `good first issue`, automated build checks, and contributor documentation should be there early.

One practical limitation: unit tests and normal .NET builds can run in GitHub CI, but real Revit integration tests require a suitable Windows environment with licensed Revit installed. Also, don't redistribute Autodesk's proprietary API binaries in the public repository.

### Development roadmap

| Stage             | Scope                                                                          | Completion milestone                     |
| ----------------- | ------------------------------------------------------------------------------ | ---------------------------------------- |
| Foundation        | C# solution, Revit add-in, operation layer, WPF, basic CLI                     | Native tool can inspect and modify Revit |
| MCP               | 8–12 generic tools, discovery, read/write execution, Codex external connection | Codex completes reliable scripted tasks  |
| Native utilities  | View Range + Room Dimensions                                                   | Both work by button and MCP              |
| Dynamic execution | Roslyn C# query/modify, transactions, disposable test models                   | Cabin Eval can execute and be scored     |
| Built-in Agent    | Codex App Server integration, sign-in, sessions, skills                        | User can work without leaving Revit      |
| Exploration       | Optional visual planning and reflection-based discovery                        | Demonstrated improvement over baseline   |

The first public release doesn't need every item. I'd prioritize a great installation experience, functioning native tools, and a reliable MCP connection over a polished chat experience that isn't yet useful.

## 9. Decisions I'd carry forward

Keep

All C#/.NET, WPF, a single repository and installer, native tools, an MCP interface, a robust CLI, reusable skills, and the Cabin Eval.

Refine

File-copy safety into reversibility suited to Revit; the Codex harness into an optional Agent interface; visual planning into a lightweight, measurable experiment.

Defer

Full reflection-based API invocation, advanced whiteboarding, additional model providers, cloud infrastructure, and sophisticated autonomous workflows.

Avoid

Building our own LLM orchestration runtime, maintaining independent implementations for CLI/MCP/UI, or treating simple sketches as proof that a Revit model is correct.

## The vision I'd adopt

> RevitThyme is an open-source, native Revit toolkit that makes Autodesk Revit easier to use, automate, and extend.
>
> It provides practical tools for everyday BIM work, a common operation layer accessible through its UI, CLI, and MCP, and an optional AI interface powered by existing agent runtimes.
>
> Its goal is to give users and AI agents powerful access to Revit while making complex workflows repeatable, inspectable, and reversible wherever practical.

One last design decision I consider especially important: RevitThyme should be AI-agnostic at its foundation and Codex-first in its initial experience.

That allows us to make Codex integration excellent without making Codex a permanent architectural dependency.

And I'd make your planning-canvas idea a specific research experiment: compare the Cabin Eval with and without quick planning, then inspect the resulting model quality, execution time, and tool calls. If it improves outcomes, expand it. If it doesn't, we discard it without disrupting the product.

That is the approach I'd take to keep RevitThyme ambitious without allowing interesting side projects to consume its core mission.
