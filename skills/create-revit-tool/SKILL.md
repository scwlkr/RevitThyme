---
name: create-revit-tool
description: Turn a plain-language request into a saved reusable Revit C# tool with inputs, expected results and executable tests.
---

1. Inspect the exact document and relevant Revit data with MCP. Resolve the requested behavior and inputs; prefer existing typed operations for immediate tasks they cover. A request to save a tool authorizes creating its local definition, not running its model changes.
2. Generate one C# method body using `doc`, `uiapp`, `cancellationToken` and the provided `inputs` JsonElement. Read inputs with `inputs.GetProperty("name")`; optional inputs use TryGetProperty. The host owns the transaction. Use fully qualified Autodesk types or the existing compiler imports. Reserve `inputs` and `__revitThymeInputs` for the runtime. Return JSON data within 8 KiB. Define mode as query (current-document rollback) or modify (one Undo).
3. Define clear typed inputs: unique letter-first identifiers, description, type (`string`, `number`, `integer`, `boolean`, `string[]`) and required flag. Use Revit internal units and native UniqueIds where needed. Record the original request, tool name, description and expected result.
4. Define `resultChecks` before execution. Each named check independently reads Revit and returns `{ exists = true, value = nativeValue }` (use false for a missing native target). Use `equals` with one `expected` JSON value or `expectedInput` name; use `exists`, `absent`, or inclusive numeric `range` with minimum/maximum where appropriate. Checks receive `doc`, `uiapp`, `cancellationToken`, `inputs`, `result` (original script JSON), and `changes` (authoritative native change IDs); certify native reads rather than the script's success claim. Define `allowedChangesSource` that reads only pre-action native state/inputs and returns `{ modified = new long[] { permittedNativeIds }, deleted = new long[] { permittedNativeIds } }`. Permit additions only with reviewed `maxAdded` and negative native `addedCategoryIds`. Use empty arrays/count zero for changes the action must not make. The plan is part of the reviewed saved digest.
5. Attach at least one concrete test: name, example inputs matching the contract, disposable-fixture assumptions, expected result and a C# AssertionSource that reads Revit and returns boolean true only when that result holds. For data-only query tools the assertion can independently calculate/check the intended result. Include failure conditions. Keep source plus encoded inputs within 24 KiB. These manual assertions are separate from automatic runtime result checks.
6. Call save_tool with a new lowercase nonempty GUID toolId and the complete definition. Reuse that ID only to recover an identical save; changed definitions require a new ID. Report the returned ID, digest, input contract and test assumptions. A saved definition has testStatus not_run; claim verification only from actual execution evidence.
7. When execution is requested, retrieve with get_tool, review the exact source/digest and validate targets. Require the trusted-code host opt-in and user intent; C# has full process permissions and no sandbox. Call run_tool with the reviewed digest, input object, a fresh get_context capture, unique request GUID and trusted=true. Require `verification.status=passed` for a configured plan; inspect named checks, expected/observed values and unexpected native IDs. Applied plus failed/error/unconfirmed means the action may already be committed: stop and report both outcomes. Automatic checks never Undo or rerun the action. Recover with verify_tool using the original request ID, digest and inputs; poll get_operation for an uncertain original action. Retained checks report their original observation; an intervening revision cannot be newly certified.
8. To manually validate on an explicitly disposable fixture, run the tool with its test inputs, refresh context and run_tool with the same inputs and testName to execute its stored assertion as a rollback query. Require a successful native result whose execution.value is boolean true, independently read back important model values, and restore modifications using the recorded Undo or exact prior value. An assertion error/false is a failed test. Report test evidence and limitations; this feature does not persist test status or manage fixture runs.

For standalone C# workflows, use prepare_result_checks with the original action request ID, exact action source SHA-256, plan, inputs and capture before submitting the action. Require a successful preparation receipt, execute once at that same capture, then call verify_result with identical binding arguments. Recover these original deterministic preparation/verification IDs; keep the original action ID after timeout. Observers run outside an active transaction and discard detected checker transactions; full-process trusted C# still has external effects outside this guard. Limits: 1–16 checks, 24 KiB aggregate observation source, 8 KiB returned observation JSON, 32 KiB separate observation data and 512 native changed IDs. Missing, malformed, oversized or stale evidence never passes.
